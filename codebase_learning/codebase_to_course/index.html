The Journey

What actually happens when you type /apply

AI Job Search is a free toolkit built on top of Claude Code. It turns Claude Code into a personal job-application team: it checks whether a job posting is a good fit for you, drafts a tailored two-page CV and cover letter, and preps you for interviews. A geophysicist built it to land his own AI engineering job — then open-sourced it.

This module follows one command through the whole system, start to finish, so you can see the machinery behind the result.

The key insight: it's just a checklist

Here's the part that surprises most people. apply.md isn't a hidden program or a black box — it's a Markdown file, the same kind of plain-text file you'd use for a to-do list. Claude Code reads it top to bottom and follows it like a recipe.

CODE 

# /apply - Drafter-Reviewer Job Application Workflow

You are orchestrating a two-agent job application workflow. The job posting is provided below as `$ARGUMENTS` (either a URL or pasted text).

Follow these steps **exactly in order**. Do not skip steps.

**Token-efficiency rules for this workflow:**
- Never re-Read a file whose contents are already in your context from an earlier step. If you read it in Step 1, it is still available in Step 2.
- When dispatching the reviewer agent, pass draft content **inline in the agent prompt** rather than asking the agent to Read files you already have in memory.
- Run the full verification checklist exactly once, at the end (Step 6). The reviewer focuses on content critique, not verification.
- Step 5 (compile and inspect PDFs) is mandatory and non-skippable...
PLAIN ENGLISH

This is the title of the recipe, and a reminder that two AI helpers are involved: one drafts, one reviews. Whatever you pasted after /apply — a link or raw text — gets stored in a placeholder called $ARGUMENTS.

A firm rule: go through the steps in order, don't improvise, don't skip ahead.

These are cost-saving habits: don't make Claude re-read a file it already has in memory, and don't waste a second AI's time re-fetching things the first one already found.

Save the big "check everything" pass for the very end, once, instead of repeating it after every step.

Some steps are flagged as unskippable because skipping them causes real, hard-to-spot problems later — like a CV that looks fine in the source file but renders broken.

💡
There's no hidden server

No database, no login, no cloud backend running somewhere. The "code" here is mostly plain-English instructions that an AI reads and follows, step by step, in a folder on your own computer.

Step 0: the very first thing Claude does

Before anything else, Claude has to figure out what you actually gave it.

CODE 

## Step 0: Parse Input

- If `$ARGUMENTS` looks like a URL, use `WebFetch` to retrieve the job posting content.
- If it is pasted text, use it directly.
- Extract: **company name**, **role title**, **department** (if mentioned), **location**, and **language** of the posting (Danish or English).
- Store these for use throughout the workflow.
PLAIN ENGLISH

Claude checks: does what you gave it look like a web link?

If it's a link, Claude uses a tool called WebFetch to go open that page and read it. If you pasted the job description directly instead, Claude skips fetching and just reads what you typed.

Either way, Claude then pulls out the specific facts it'll need later: company name, job title, department, location, and whether the posting is in Danish or English.

Those facts get kept in Claude's memory for every later step — nobody has to re-explain them.

Meet the Cast

Skills, commands, subagents, and CLI tools — the four kinds of files behind every AI job-search action.

In Module 1 you watched /apply fetch a job posting. That fetching step didn't happen by magic. It happened because a specific kind of file told Claude exactly how.

This module meets the four kinds of files that make up the whole cast. Think of the repo as a theater company running backstage: every file is a role, and every role behaves differently once the curtain goes up.

Four Roles, Four Jobs

A command is the script cue-card an actor is handed at showtime: "say this line now." A skill is the actor's full training and standing instructions, reusable across many shows.

A subagent is a stunt double: brought in for one dangerous scene, given a fresh briefing, and sent home when the scene wraps. A CLI tool is a stagehand who only does one physical task — raise the curtain — when cued, and doesn't act at all.

🎬

Inside a Skill's Training Sheet

Skills are the role with real YAML frontmatter. Commands are just plain markdown starting with a heading — no frontmatter needed. Here's the real training sheet for the freehire-search skill.

CODE

version: 1.0.0
description: >
  Use this skill to search live software / tech / data / engineering job listings
  across many countries and markets (and remote) via the freehire.dev aggregator's
  public API, or to look up a specific posting. It aggregates roles from ~50 ATS
  platforms into one schema, so a single skill covers many markets — but its faceted
  filtering (skills, category, seniority) is tuned tech-first, so scope triggers to
  technical roles. Trigger phrases: find a tech job, software job search, developer
  jobs, engineering vacancies, data/ML jobs, DevOps roles, remote developer jobs,
  "are there any <tech role> jobs in <place>", look up this freehire job posting.
context: fork
allowed-tools: Bash(bun run .agents/skills/freehire-search/cli/src/cli.ts *)
---
PLAIN ENGLISH

name is the skill's ID — how Claude and the file system refer to it internally.

description is the trigger list: the phrases that make Claude decide "this skill is relevant, load it now." This is literally how Claude discovers what tools exist for a given request.

Every scenario listed here (job search, ATS lookup) teaches Claude when to reach for this skill instead of guessing.

allowed-tools is a safety fence: this skill can ONLY run this one specific command, nothing else — it can't suddenly start deleting files or browsing the web.

💡
Good to know

A second real example, .claude/skills/job-scraper/SKILL.md, restricts its allowed-tools to Read, Write, Edit, Glob, Grep, Bash(bun --version), Bash(bun run .agents/skills/*/cli/src/cli.ts *), WebFetch, WebSearch, Agent, AskUserQuestion — a wider fence, because scraping needs to read files, call multiple CLIs, and even hand off to a subagent.

The Stagehand Doesn't Improvise

A CLI tool has its own help text, written by a human, not generated by AI judgment. Here's the actual header from the LinkedIn search tool.

CODE

03

How the Pieces Talk

The Drafter-Reviewer handoff

One author, one cold-read editor

Module 2 introduced the subagent as a stunt double with a fresh briefing. In /apply, that stunt double has a name: the Reviewer.

Think of a publishing house. The Drafter is the author who writes the full manuscript, the CV and cover letter, from scratch. Authors are bad at spotting their own mistakes; they know the text too well.

So the manuscript goes to an independent editor who has never seen a single draft of it. The editor reads it cold, researches the market, and sends back a specific edit letter, not vague notes.

📖
Opening hook

In Module 1, /apply wrote a CV and cover letter to disk. The workflow doesn't stop there: Step 3 spawns a second AI agent whose only job is to read those drafts with zero prior context and tear them apart. Here's that conversation.

Why the Reviewer starts from zero

The Reviewer is dispatched with a completely fresh context. It did not watch the Drafter write a single word.

So the Drafter must paste the CV text, cover letter text, and job posting text directly into the Reviewer's instructions. Engineers call this passing data inline.

It's also a deliberate cost-saving trick. Re-reading the same files from disk twice costs time and money; handing over text already sitting in memory is cheaper.

💡
The whole trick

A reviewer that watched the first draft get written will defend its own choices, even when it's a different AI process. A reviewer that only sees the finished draft has no ego invested in it. That's the whole trick.

The edit letter, applied mechanically

Once the Reviewer's message arrives, the Drafter doesn't re-read anything. It applies each edit straight from the JSON object using a tool called Edit.

CODE 
# .claude/commands/apply.md — Step 4
## Step 4: DRAFTER - Revise Based on Feedback

Once the reviewer agent returns its feedback:

1. **Apply Part A (structured edits) directly with the Edit tool.**
Do NOT re-read the draft files — you already have them
in context from Step 2, and the reviewer's `old_string`
values were quoted from that same text. For each edit in
the JSON array, call `Edit` with the given `file`,
`old_string`, and `new_string`. Skip any whose rationale
would require fabricating content.
PLAIN ENGLISH

This is the instruction the Drafter follows after the Reviewer replies.

For each JSON edit, the Drafter calls the Edit tool: think of old_string and new_string as a precise find-and-replace, swap this exact text for that exact text.

It never reopens the file to double-check. It already holds the draft text in memory from when it wrote it, and the Reviewer quoted old_string straight from that same text, so the match is guaranteed to line up.

Skipping the re-read matters twice over: it's faster (no extra file read), and it's cheaper (fewer tokens sent back through the AI).

If an edit would require inventing a fact rather than rewording an existing one, the Drafter skips it rather than fabricate content.

The Outside World

APIs, CLIs, and a fuzzy-matching scout that finds "Acme" inside "ACME Danmark A/S"

Back in Module 3, the Reviewer went off to research "Acme Corp's website" before approving a cover letter.

When you ran /scrape in Module 1's diagram, Claude didn't invent those job listings out of thin air. It ran real programs that fetch real web pages and real APIs.

This module opens the hood on two of them: linkedin-search and the salary lookup tool. Think of them as local scouts — each with their own beat, and their own rulebook for how to behave once they're out in the field.

Two Scouts, Two Rulebooks

One scout only walks LinkedIn's public job board. It's been told, in writing, to keep visits low-key so it doesn't get thrown out.

Another scout radios a data aggregator's official switchboard — a real API, no trespassing involved — and gets back clean, structured reports instead of having to read handwritten notes off a board.

🕵️

Scout 1: linkedin-search

Reads LinkedIn's public HTML job pages directly. No login needed, but fragile: if LinkedIn redesigns the page, the scout's notes stop making sense. Rate-limited by courtesy, not by a real contract.

☎️

Scout 2: freehire-search

Calls freehire.dev's real JSON API. A proper contract, structured data, no guesswork about layout.

💡
Both are "zero install"

Both scouts run with nothing installed beyond the bun JavaScript runtime itself. No extra libraries to trust, update, or worry about breaking.

The Noise the Scout Learns to Ignore

Danish and Nordic company names carry a lot of legal clutter. Here's the exact list the scout strips before comparing anything.

CODE 
STRIP_PATTERNS = [
    r"\ba/s\b", r"\baps\b", r"\bi/s\b", r"\bp/s\b", r"\bk/s\b",
    r"\bivs\b", r"\bamba\b", r"\ba\.m\.b\.a\.\b",
    r"\(vg\)", r"\(.*?\)",  # (VG) and other parentheticals
    r"\bdanmark\b", r"\bdenmark\b", r"\bscandinavia\b", r"\bnordic\b",
    r"\bgroup\b", r"\bholding\b",
    r",\s*.*$",  # everything after comma (sub-entities)
]
PLAIN ENGLISH

A checklist of Danish legal-entity suffixes to delete: A/S, ApS, I/S, and more.

A few more suffix types, including the German-style "amba."

Anything in parentheses, like "(VG)," gets dropped too.

Country and region words like "Danmark" or "Nordic" are noise, not identity.

So are generic corporate words like "Group" or "Holding."

And anything after a comma — usually a sub-entity name — gets chopped off.

End of the checklist.

Scoring the Match

Once both names are cleaned up, the scout scores how well they match. A perfect match scores 100. A partial containment — your query sitting fully inside a longer name — scores lower, but still counts.

CODE 
def match_score_optimized(q_norm, q_ang, q_words_set, q_words_ang_set, query, entry_name):
    """Compute a match score between 0 and 100 using precalculated query values."""
    n_norm = normalize(entry_name)

    if not q_norm or not n_norm:
        return 0

    if q_norm == n_norm:
        return 100

    if q_norm in n_norm:
        ratio = len(q_norm) / len(n_norm)
        if len(q_norm) <= 4 and ratio < 0.5:
            n_words = set(extract_core_words(entry_name))
            if not q_words_set & n_words:
                pass
            else:
                return 80 + int(ratio * 10)
        else:
            return 80 + int(ratio * 10)
PLAIN ENGLISH

This function compares your cleaned-up search text against one cleaned-up company name.

First, clean up the company name the same way the search text was cleaned.

If either side is empty after cleaning, there's nothing to compare — score 0.

If your search exactly matches the company name, score it 100. Perfect match.

If your search is fully contained inside the longer company name (like "Acme" inside "Acme Denmark A/S")...

...score it high but not perfect, based on how much of the name your search actually covers. This is how "Acme" finds "Acme Denmark A/S" automatically.

💡
Fuzzy matching, in one line

Clean the noise, then check for exact match first, then partial containment. This same two-step pattern — normalize, then compare — shows up everywhere search boxes feel "smart."

The Clever Tricks: Compile, Inspect, Iterate

Module 4 sent Claude outside the repo to gather data. Now we're back inside, for the other big feat of engineering: turning a text file into a document that actually looks right.

You've seen Claude write a LaTeX file for a CV. Here's the catch: a file that looks perfect as text can still produce a broken document.

A job title stranded alone at the bottom of page 1. Its bullet points spilling onto page 2. The source code gave no hint anything was wrong.

✂️
Think of a tailor's final fitting

Anyone can cut fabric to a pattern's exact measurements. A good tailor puts the finished garment ON the client and LOOKS at it before calling the job done — because fabric drapes unpredictably and seams bunch up in ways the paper pattern never showed. This module is about the workflow doing the equivalent for documents.

Not just cutting the pattern — trying it on

The workflow doesn't trust that the LaTeX source "looks right." It compiles a real PDF, then looks at the actual rendered pages before anyone else sees them.

Step 3 is the surprising part: Claude uses its Read tool to look at the rendered PDF pages, the same way you'd look at a finished garment on the client — not just the pattern (the .tex source) it was cut from.

CODE 

### 5a. Compile
cd cv && lualatex -interaction=nonstopmode main_<company>.tex
cd ../cover_letters && xelatex -interaction=nonstopmode cover_<company>_<role>.tex
PLAIN ENGLISH

This is step 5a of the apply workflow: actually compiling the documents.

Turn the CV's text file into a real PDF, using lualatex — the CV needs this specific compiler because a more common one breaks on the icon fonts it uses.

Do the same for the cover letter, but with xelatex instead, because the cover letter's template needs that compiler's font handling.

The checklist Claude runs against its own PDF

This is step 5b: after compiling, Claude reads the actual rendered pages and checks them against a literal pass/fail list.

CODE 

### 5b. Inspect layout
Read both PDFs via the Read tool and verify:

**CV (cv/main_<company>.pdf):**
- [ ] Exactly 2 pages (not 1, not 3)
- [ ] No orphaned \cventry titles — a job/education
      title line must never sit alone at the bottom of
      page 1 with its bullets on page 2. This is the
      most common failure.
- [ ] Section headings are not isolated at the top of
      page 2 with only 1-2 lines below
- [ ] No awkward whitespace gaps
PLAIN ENGLISH

A 2-page CV that compiles to 1 or 3 pages failed — the content doesn't fit the format, something has to change.

The most common bug: imagine flipping to a résumé and seeing only a company name and dates at the very bottom of a page — you'd have to turn the page just to find out what the person actually did there. That's what this line catches.

A section title (like "Experience") shouldn't be the last thing on a page, or sit at the top of a new page with almost nothing under it — both look broken to a reader.

Big empty gaps mean LaTeX's automatic spacing did something ugly. A human eye catches this; the source text never shows it.

Two different repairs, for two different problems

A tailor doesn't handle a loose thread and a too-short hem the same way. This workflow makes the same distinction between a near-miss and real overflow.

Near-miss: pin the seam. If a title is about to get orphaned, add a hint in the preamble that tells the compiler "keep this block together."

CODE 

\needspace{5\baselineskip}
\item{\cventry{YEAR--YEAR}{Role Title}{Organization}{Location}{}{...}}
PLAIN ENGLISH

"Before starting this entry, make sure there's room for at least 5 lines below it — otherwise push the whole thing to the next page instead of splitting it."

The actual job entry, now protected from being orphaned. (Requires adding \usepackage{needspace} up in the preamble.)

Real overflow: alter the garment. If a CV is genuinely too long, don't trim mechanically by section — score every line and cut the weakest one first.

1
Relevance to this posting

Does the line name a tool, keyword, or responsibility the job ad actually asks for?

2
Uniqueness

Is this the only place the claim appears, or is it repeated elsewhere on the CV?

3
Narrative load

Does the cover letter depend on this line? Cutting it would force a rewrite elsewhere.

Whichever line scores lowest gets cut first — regardless of which section it happens to sit in. An older role that speaks directly to the posting can outrank a recent one that doesn't.

Clever tricks worth asking any AI tool for

None of this is specific to CVs or LaTeX. These are habits worth requesting whenever an AI tool generates something you'll rely on.

👁️

Render before you trust

Don't just read the source — compile it, run it, or render it, then look at the real output before calling it done.

⚖️

Score before you cut

When something must be trimmed, weigh each piece by relevance and impact — don't cut mechanically by position or section.

🧵

Match the fix to the problem

A near-miss gets a nudge (\enlargethispage), not a cut. The project's own rules say it plainly: don't cut to fit if the fit is borderline (2.02 pages).

Guardrails: How the Framework Protects Every Fork

Module 5 watched Claude catch its own mistakes on a single PDF. This module zooms all the way out: how the maintainers catch risky changes before they reach every single person who forks this repo.

This whole framework runs on your machine, using your Claude Code permissions. Thousands of other job-seekers fork this exact repo and inherit whatever it ships.

Imagine someone quietly changed the fork's setup so Claude could "run any command" instead of just "run this one salary-lookup script." Every future fork would silently inherit that risk.

🚧
The problem this module solves

Nobody reviewing that change would necessarily notice one word changed in a config file. This module is about the code that makes sure they do notice.

Not a security guard. A fire-code inspector.

A security guard stands at the door and stops people from entering. That's not what this system does.

🏢
The building's owners can still change things

Add a balcony, repaint a hallway, rearrange furniture — nobody stops them.

🔥
But some changes trigger an inspection

Rewiring the electrics or adding a new door has to be flagged, documented, and signed off — precisely because those are the changes most likely to hurt someone if done carelessly.

💡
The core idea

These guardrails don't block change. They force the riskiest changes to be visible and deliberate, so a human has to look at them on purpose.

Meet the inspector: security_guards.py

Two small Python scripts run automatically in CI — via .github/workflows/ci.yml — on every proposed change to this repo. Here is the file's own explanation of its job, taken directly from its top comment:

CODE 
#!/usr/bin/env python3
"""Supply-chain guards for the template's riskiest surfaces.

Run from anywhere: python tools/security_guards.py

This repo ships pre-approved Claude Code permissions and CLI code that every
fork user executes. These guards make the dangerous changes LOUD, not
impossible: a PR that intentionally needs one of them must update the
allowlists in this file in the same diff, so the change is explicit and
reviewable rather than buried.

Checks:
1. .claude/settings.json — every permissions.allow entry must be in the exact
   allowlist below. Catches permission widening (e.g. Bash(*), Bash(curl:*)),
   which would auto-approve commands on every fork.
2. .gitignore — the personal-data ignore rules must all still be present.
   Catches weakening that would make future users silently commit their
   tracker, profile exports, or application archives.
3. .agents/**/package.json — no npm/bun lifecycle scripts (preinstall,
   install, postinstall, prepare, prepack) and no trustedDependencies.
   Catches code execution smuggled into `bun install`.

Stdlib only. Exit 0 on success, 1 with a failure list otherwise.
"""
PLAIN ENGLISH

This is the file's own "job description," written for whoever opens it next.

Every fork runs this file's permissions and code. If those get quietly widened, everyone inherits the risk.

Check 1: does the list of approved Claude Code permissions still match the known-safe list?

Check 2: are the rules that keep your personal data (CV, salary data, tracker) out of Git still intact?

Check 3: can any installed tool sneak code execution into the install step?

It uses only Python's built-in stdlib, and fails loudly (exit code 1) if anything looks off.

Two lists that must match, exactly

The repo ships an allowlist in two places: the real settings Claude Code reads, and a second copy the checker compares against.

CODE: .claude/settings.json 
{
  "permissions": {
    "allow": [
      "Skill(job-application-assistant)",
      "Bash(bun run:*)",
      "Bash(python salary_lookup.py:*)",
      "Bash(python3 salary_lookup.py:*)",
      "Bash(pdftotext:*)"
    ]
  }
}
PLAIN ENGLISH

This is the real file Claude Code reads on your machine. Anything listed here runs without asking you first.

Five entries, each narrow: one skill, one bun command, two ways to run salary_lookup.py, and pdftotext.

Notice what's missing: nothing here says "run any Bash command."

CODE: tools/security_guards.py 
# The exact permission entries the template ships. A PR that adds or changes
# an entry must add it here too - that is the point: the diff shows both.
ALLOWED_PERMISSIONS = {
    "Skill(job-application-assistant)",
    "Bash(bun run:*)",
    "Bash(python salary_lookup.py:*)",
    "Bash(python3 salary_lookup.py:*)",
    "Bash(pdftotext:*)",
}
PLAIN ENGLISH

This is the checker's own private copy of "known good" permissions.

It's deliberately independent of settings.json — a second, separately-maintained source of truth to compare against.

If someone edits settings.json without touching this list too, the two stop matching. That mismatch is exactly what gets caught.

When the lists don't match: loud, not silent

Here is the actual check that compares the two lists and decides what to do about a mismatch.

CODE 
    for entry in allow:
        if entry not in ALLOWED_PERMISSIONS:
            errors.append(
                f".claude/settings.json: permission not in the reviewed allowlist: {entry!r}. "
                "Pre-approved permissions run without prompting on every fork. If this entry is "
                "intentional, add it to ALLOWED_PERMISSIONS in tools/security_guards.py in the "
                "same PR so the widening is explicit and reviewable."
            )
    for entry in ALLOWED_PERMISSIONS - set(allow):
        # Not an error: settings may legitimately drop an entry. But an
        # allowlist entry that no longer exists should be pruned.
        print(f"note: allowlisted permission not present in settings.json: {entry!r}")
PLAIN ENGLISH

For every permission actually in settings.json, check it's on the known-good list.

If it isn't, don't just fail — explain exactly which entry is the problem and exactly what to do about it.

The fix is spelled out in the error itself: add it to ALLOWED_PERMISSIONS, in the same pull request, so a reviewer sees the widening on purpose.

The reverse case (a list entry no longer used) is just a friendly note, not a failure — removing a permission is safe, adding one isn't.

💡
Aha!

Guardrails that fail loudly and specifically — naming the exact file, the exact fix — are far more useful than guardrails that just say "blocked." When you ask an AI to add a safety check to your own project, ask for an error message that tells the next person exactly what to do, the way this one does.
