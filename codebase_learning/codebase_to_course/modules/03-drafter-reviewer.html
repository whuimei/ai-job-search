How the Pieces Talk

The Drafter-Reviewer handoff

One author, one cold-read editor

Module 2 introduced the subagent as a stunt double with a fresh briefing. In /apply, that stunt double has a name: the Reviewer.

Think of a publishing house. The Drafter is the author who writes the full manuscript, the CV and cover letter, from scratch. Authors are bad at spotting their own mistakes; they know the text too well.

So the manuscript goes to an independent editor who has never seen a single draft of it. The editor reads it cold, researches the market, and sends back a specific edit letter, not vague notes.

Why the Reviewer starts from zero

The Reviewer is dispatched with a completely fresh context. It did not watch the Drafter write a single word.

So the Drafter must paste the CV text, cover letter text, and job posting text directly into the Reviewer's instructions. Engineers call this passing data inline.

It's also a deliberate cost-saving trick. Re-reading the same files from disk twice costs time and money; handing over text already sitting in memory is cheaper.

💡
The whole trick

A reviewer that watched the first draft get written will defend its own choices, even when it's a different AI process. A reviewer that only sees the finished draft has no ego invested in it. That's the whole trick.

The edit letter, applied mechanically

Once the Reviewer's message arrives, the Drafter doesn't re-read anything. It applies each edit straight from the JSON object using a tool called Edit.

CODE 
# .claude/commands/apply.md — Step 4
## Step 4: DRAFTER - Revise Based on Feedback

Once the reviewer agent returns its feedback:

1. **Apply Part A (structured edits) directly with the Edit tool.**
Do NOT re-read the draft files — you already have them
in context from Step 2, and the reviewer's `old_string`
values were quoted from that same text. For each edit in
the JSON array, call `Edit` with the given `file`,
`old_string`, and `new_string`. Skip any whose rationale
would require fabricating content.
PLAIN ENGLISH

This is the instruction the Drafter follows after the Reviewer replies.

For each JSON edit, the Drafter calls the Edit tool: think of old_string and new_string as a precise find-and-replace, swap this exact text for that exact text.

It never reopens the file to double-check. It already holds the draft text in memory from when it wrote it, and the Reviewer quoted old_string straight from that same text, so the match is guaranteed to line up.

Skipping the re-read matters twice over: it's faster (no extra file read), and it's cheaper (fewer tokens sent back through the AI).

If an edit would require inventing a fact rather than rewording an existing one, the Drafter skips it rather than fabricate content.
