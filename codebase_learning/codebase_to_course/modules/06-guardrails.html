Guardrails: How the Framework Protects Every Fork

Module 5 watched Claude catch its own mistakes on a single PDF. This module zooms all the way out: how the maintainers catch risky changes before they reach every single person who forks this repo.

This whole framework runs on your machine, using your Claude Code permissions. Thousands of other job-seekers fork this exact repo and inherit whatever it ships.

Imagine someone quietly changed the fork's setup so Claude could "run any command" instead of just "run this one salary-lookup script." Every future fork would silently inherit that risk.

🚧
The problem this module solves

Nobody reviewing that change would necessarily notice one word changed in a config file. This module is about the code that makes sure they do notice.

Not a security guard. A fire-code inspector.

A security guard stands at the door and stops people from entering. That's not what this system does.

🏢
The building's owners can still change things

Add a balcony, repaint a hallway, rearrange furniture — nobody stops them.

🔥
But some changes trigger an inspection

Rewiring the electrics or adding a new door has to be flagged, documented, and signed off — precisely because those are the changes most likely to hurt someone if done carelessly.

💡
The core idea

These guardrails don't block change. They force the riskiest changes to be visible and deliberate, so a human has to look at them on purpose.

Meet the inspector: security_guards.py

Two small Python scripts run automatically in CI — via .github/workflows/ci.yml — on every proposed change to this repo. Here is the file's own explanation of its job, taken directly from its top comment:

CODE 
#!/usr/bin/env python3
"""Supply-chain guards for the template's riskiest surfaces.

Run from anywhere: python tools/security_guards.py

This repo ships pre-approved Claude Code permissions and CLI code that every
fork user executes. These guards make the dangerous changes LOUD, not
impossible: a PR that intentionally needs one of them must update the
allowlists in this file in the same diff, so the change is explicit and
reviewable rather than buried.

Checks:
1. .claude/settings.json — every permissions.allow entry must be in the exact
   allowlist below. Catches permission widening (e.g. Bash(*), Bash(curl:*)),
   which would auto-approve commands on every fork.
2. .gitignore — the personal-data ignore rules must all still be present.
   Catches weakening that would make future users silently commit their
   tracker, profile exports, or application archives.
3. .agents/**/package.json — no npm/bun lifecycle scripts (preinstall,
   install, postinstall, prepare, prepack) and no trustedDependencies.
   Catches code execution smuggled into `bun install`.

Stdlib only. Exit 0 on success, 1 with a failure list otherwise.
"""
PLAIN ENGLISH

This is the file's own "job description," written for whoever opens it next.

Every fork runs this file's permissions and code. If those get quietly widened, everyone inherits the risk.

Check 1: does the list of approved Claude Code permissions still match the known-safe list?

Check 2: are the rules that keep your personal data (CV, salary data, tracker) out of Git still intact?

Check 3: can any installed tool sneak code execution into the install step?

It uses only Python's built-in stdlib, and fails loudly (exit code 1) if anything looks off.

Two lists that must match, exactly

The repo ships an allowlist in two places: the real settings Claude Code reads, and a second copy the checker compares against.

CODE: .claude/settings.json 
{
  "permissions": {
    "allow": [
      "Skill(job-application-assistant)",
      "Bash(bun run:*)",
      "Bash(python salary_lookup.py:*)",
      "Bash(python3 salary_lookup.py:*)",
      "Bash(pdftotext:*)"
    ]
  }
}
PLAIN ENGLISH

This is the real file Claude Code reads on your machine. Anything listed here runs without asking you first.

Five entries, each narrow: one skill, one bun command, two ways to run salary_lookup.py, and pdftotext.

Notice what's missing: nothing here says "run any Bash command."

CODE: tools/security_guards.py 
# The exact permission entries the template ships. A PR that adds or changes
# an entry must add it here too - that is the point: the diff shows both.
ALLOWED_PERMISSIONS = {
    "Skill(job-application-assistant)",
    "Bash(bun run:*)",
    "Bash(python salary_lookup.py:*)",
    "Bash(python3 salary_lookup.py:*)",
    "Bash(pdftotext:*)",
}
PLAIN ENGLISH

This is the checker's own private copy of "known good" permissions.

It's deliberately independent of settings.json — a second, separately-maintained source of truth to compare against.

If someone edits settings.json without touching this list too, the two stop matching. That mismatch is exactly what gets caught.

When the lists don't match: loud, not silent

Here is the actual check that compares the two lists and decides what to do about a mismatch.

CODE 
    for entry in allow:
        if entry not in ALLOWED_PERMISSIONS:
            errors.append(
                f".claude/settings.json: permission not in the reviewed allowlist: {entry!r}. "
                "Pre-approved permissions run without prompting on every fork. If this entry is "
                "intentional, add it to ALLOWED_PERMISSIONS in tools/security_guards.py in the "
                "same PR so the widening is explicit and reviewable."
            )
    for entry in ALLOWED_PERMISSIONS - set(allow):
        # Not an error: settings may legitimately drop an entry. But an
        # allowlist entry that no longer exists should be pruned.
        print(f"note: allowlisted permission not present in settings.json: {entry!r}")
PLAIN ENGLISH

For every permission actually in settings.json, check it's on the known-good list.

If it isn't, don't just fail — explain exactly which entry is the problem and exactly what to do about it.

The fix is spelled out in the error itself: add it to ALLOWED_PERMISSIONS, in the same pull request, so a reviewer sees the widening on purpose.

The reverse case (a list entry no longer used) is just a friendly note, not a failure — removing a permission is safe, adding one isn't.

💡
Aha!

Guardrails that fail loudly and specifically — naming the exact file, the exact fix — are far more useful than guardrails that just say "blocked." When you ask an AI to add a safety check to your own project, ask for an error message that tells the next person exactly what to do, the way this one does.

A second inspection point: install-time code

This repo installs third-party job-portal search tools. The checker also blocks a well-known supply-chain trick: code that runs automatically the moment you install a package.

CODE 
FORBIDDEN_SCRIPTS = {"preinstall", "install", "postinstall", "prepare", "prepack"}
PLAIN ENGLISH

These are the names of lifecycle scripts: hooks that package managers run automatically at set moments, like right after install.

CODE 
        bad = FORBIDDEN_SCRIPTS & set(scripts)
        if bad:
            errors.append(
                f"{relpath}: lifecycle script(s) {sorted(bad)} are forbidden - they execute "
                "arbitrary code during `bun install` on every fork user's machine."
            )
PLAIN ENGLISH

If any installed tool's package.json defines one of those forbidden scripts, that's an error.

Why it matters: that code would run silently on every fork user's machine the moment they type bun install, before any human looks at it.
